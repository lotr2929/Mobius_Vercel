# Mobius — CLAUDE.md

Personal AI chat with tiered memory (PCM) and web search. Rewritten 1 Oct 2026; the previous version is in `..\Mobius(old)` and in git history.

## Keep (the three fixed points)
1. Free cloud models, kept current (see "The model stack" below)
2. Supabase as the memory store (shared "dlbs" project, `mobius_` tables)
3. Simple chat UI (`frontend/index.html`, vanilla JS)

## The model stack (`backend/ai/models.js` is the single list)
- Each model is tagged with strengths (general, reasoning, code, fast, long-context, multilingual) and ranked per role: `chat` (answers), `quick` (routing), `deep` (big summaries), `learn` (deciding what to remember).
- Prefer `-latest` aliases where a provider offers them; they follow new releases by themselves.
- A model that fails is skipped for a while, worked out from the provider's own error (`restFor` in `cascade.js`, 6 Oct 2026): a spent **daily** allowance rests until its reset but never more than 3 h (so it is rechecked; a refused call costs under a second), a per-minute limit for the delay named (15 s to 1 h, else 1 min), 402/403/404/bad key 6 h, a timeout 20 s. Rests are shared between instances in `mobius_state` key `model_rest` (`syncRest`), because Vercel starts fresh processes. Settings shows "resting until HH:MM UTC". Free-tier limits are per model.
- **Keeping it current:** `npm run models` (add `-- --probe` for a tiny live call per model) compares the list with what each provider offers: it flags retired models (skipped automatically) and lists new ones. The same audit runs inside the 6-hourly maintenance. Review its "worth a look" list and update `models.js`.
- Learned the hard way (Oct 2026): Groq retired llama-3.3-70b; Cerebras and Mistral Small/Medium/Magistral and all Gemini Pro models are closed to these free keys. Check access with `--probe`, not just the model list.
- **Free quotas are per model (4 Oct 2026):** the 3.8 and 3.7 Flash allowances ran out for two days while 3.6, 3.5, 3.5-lite and 3-flash-preview still answered, so each extra Gemini Flash version is another quota. The chat order is deliberate: strongest first (Gemini 3.8, 3.7, 3.6, 3.5, gpt-oss-120b, 3-flash-preview, Qwen3.8-27B, then NVIDIA's Nemotron 3 Ultra and Super), the small models (ministral-14b, gpt-oss-20b) last, after one of them answered an old question from the memory block. Mistral Small/Medium/Magistral answer 429 on every request and Large is tier-blocked on this key; the bigger open models (Kimi K3, DeepSeek V4, GLM-5.3) are not free by API (Ollama Cloud went credit-based on 31 Aug 2026).
- **NVIDIA NIM** (`provider: 'nvidia'`, key `NVIDIA_API_KEY`, endpoint integrate.api.nvidia.com/v1; free with the NVIDIA Developer Program; the key is on the Vercel *project* as well as in `.env` and `.master-env.var`). Tried live 4 Oct 2026: **nemotron-3-ultra and nemotron-3-super answer in 1–2 s**; glm-5.3-flash takes ~30 s to a first token (kept as a late fallback); deepseek-v4.1-flash ~36 s (not registered); kimi-k3, glm-5.3 and gemma-4-31b timed out at 60 s (not registered); kimi-k2.6, mistral-large and llama-3.1-nemotron-ultra are "not found for account"; MiniMax M3 and gpt-oss-120b are not on NVIDIA's list. These are reasoning models: only `delta.content` is streamed, so the answer starts after the thinking (a short pause). NVIDIA's free endpoints are "trial use only: no personal or confidential data", and Mobius sends the profile and memory with each message, so they sit below the Gemini models. The first `--probe` run showed 401 for every NVIDIA model only because `probeModels()` sent NVIDIA requests to Mistral's URL (fixed); the key itself was fine.
- `runCascade(..., { task: 'code' })` tries models tagged for that task first; nothing sets it yet. Intended for the later "best model per job" routing.

## How a message is handled (`backend/chat.js`)
1. Load the last 20 messages (complete question+answer pairs only) verbatim.
2. `pcm/router.js` makes one cheap model call: standalone rewrite of the message, search queries, which projects it concerns, whether the archive, the web or Mobius's own documentation is needed. Rule-based fallback if every model fails.
3. Recall in parallel: profile, week digest, archive search, named document, web search (Tavily, skipped when the answer is already in hand).
4. `pcm/assemble.js` builds a budgeted context pack (about 30K chars; sections ranked, lowest-ranked cut first).
5. Stream the answer from the cascade; save the question and answer together; embed a few backlog rows in the background.

Memory failures never stop the chat; each recall step degrades to "nothing found".

## Debugging (read this first when something looks wrong)
- Every chat turn writes a **trace** to `mobius_traces` (14 days kept, RLS on): the question, the router's plan, what was recalled, the exact prompt sent, which model answered, fallbacks, timings, errors. Browser errors are reported there too.
- Read them: `select id, created_at, data->>'query', data->>'model', data->'plan', data->'marks' from mobius_traces order by id desc limit 5;` in the Supabase SQL Editor (or via the Supabase connector), or `GET /api/debug/traces?n=5` and `/api/debug/trace/<id>` (login required on the live site).
- Fixed on 2 Oct 2026 (found by trace): a question whose answer failed was saved alone, then merged into the *next* question and answered in its place. Now pairs are saved together and unanswered rows are ignored.

## Notes: remembering what Boon asks, and finding what he would want (`pcm/notes.js`)
- **Commands** are plain sentences at the start of a message, matched by rules (no model needed, so they work even when every model is down): `Remember that ...` / `Note: ...` / `Keep in mind ...` / `From now on ...` save a note at once; `Forget ...` or `Forget #14` removes one; `Show notes`; `Show suggestions`; `Save 14, 16` / `Save all`; `Drop 15` / `Drop all`.
- **Learning as he talks** (`pcm/learn.js`; mode chosen in Settings, default from config `LEARN_MODE`): the `learn`-role model reads each message alongside the assistant's previous reply and what is already saved. In `auto` mode an *explicit* definition of his own term, correction of the assistant, or standing preference is saved at once; the reply ends with a line saying what was noted and how to undo it (`forget #14`). Anything less certain becomes a suggestion. It runs in parallel with the answer (starts at the first token), so it adds no waiting time. Found necessary after the model guessed the meaning of his own term "Scriptura Fidelium" wrongly.
- Active notes (table `mobius_notes`) are sent to the model with every message (all of them if they fit in 3,000 chars, else the most relevant plus the newest).
- **Review job** (`harvestNotes` in `pcm/maintain.js`, part of the 6-hourly maintenance): a model reads new conversation, compares it with notes, profile and projects, and *suggests* up to 8 notes per batch. Suggestions from the review job stay `proposed` until Boon says "save"; at the start of a conversation Mobius mentions that some are waiting. First run read the whole history. Max 20 waiting at a time. Rejected or forgotten notes are not suggested again.
- **No review needed (4 Oct 2026).** Boon does not review suggestions and wants no reminders about them (removed from `buildSystem`; a test pins it). Only `active` notes reach any prompt; `proposed` ones do nothing. So the maintenance step `promote` (`notes.js promoteSuggestions`) turns a suggestion older than 6 hours into an active note (`source: suggested-auto`, at most 12 a run, oldest first), unless it repeats an active note (word overlap ≥ 0.6: marked rejected) or touches a **private topic** (`PRIVATE_TOPIC`: health, medication, money, identifiers and passwords, legal trouble, sex and relationships, immigration, personal strain or grief, spouse/home life). Private ones stay `proposed` for ever (they lapse after 60 days) and are never sent to a model, because active notes ride in every prompt, including those to free tiers that may train. Watch the first weeks: if a promoted note is wrong, Boon will say so in chat and the fix is structural (tighten the review prompt in `harvestNotes` or the filter), not a chore for him.
- Not yet built: folding long-lived notes into the profile; semantic (embedding) selection when notes outgrow the prompt.

## Conversation continuity
One continuous stream (there is no separate "conversation" object). The last 20 messages (10 exchanges) go to the model verbatim; older material arrives as the week digest, recent un-digested lines, project notes and archive search. The UI's reset button only clears the screen.

## Syncing devices
All state is in Supabase, so the phone and laptop (and the local server and Vercel) share one history and memory. Each device refreshes its history list every 30 seconds and when the app regains focus; the arrows then include exchanges from the other device. A question and its answer are written in one insert, so two devices chatting at once never interleave.

## The four memory tiers
| Tier | Holds | Stored in | Refreshed by |
|---|---|---|---|
| 1 Immediate | last 20 messages verbatim + 7-day digest | `mobius_messages`, `mobius_memory` kind `week` | digest: `pcm/maintain.js` |
| 2 Personal | profile of Boon (target 3,000 chars; a longer one is condensed by a model) | `mobius_memory` kind `profile` | weekly update, used at once; Boon edits it in Settings |
| 3 Current | one note per project active in the last 30 days | `mobius_memory` kind `project` | incremental, from new messages |
| 4 Archive | every message and document | `mobius_messages`, `mobius_docs`, `mobius_docs_full` | live; embeddings filled in the background |

Archive search is hybrid (vector + keyword, fused in SQL: `pcm_search_messages`, `pcm_search_docs`). With Gemini's quota exhausted it degrades to keywords only.

## Development notes: Boon's to-do list for Mobius (READ AT THE START OF EVERY SESSION)
- Boon types instructions and improvements into Settings > Development notes from any device. Stored in `mobius_devnotes` (Supabase); on the laptop a readable copy of the open items is kept in `_dev\devnotes.md`. Never sent to any AI model.
- **At the start of a session:** read the open items (`select id, content, created_at from mobius_devnotes where status = 'open' order by id;` via the Supabase connector, or `GET /api/devnotes`), tell Boon what is waiting, and work through them with him.
- **When one is finished:** mark it done with a line saying what was done: `update mobius_devnotes set status = 'done', done_at = now(), result = '...' where id = N;`. Boon sees it under Done in Settings.
- Removed notes go to the backup like everything else (`devnote` kind); finished ones are retired after 90 days.

## Reading a whole folder: digests (`docs/digest.js`, table `mobius_digests`)
- Search finds passages; it cannot answer "what runs through all of these?" because no model has seen the whole. So every document is **digested once, in advance** (maintenance step `digests`): its text is cut into ~16,000-character sections (small enough for every model in the stack), a `deep`-role model writes a ~150–200-word digest of each (`level='section'`), and those are folded in order into one ~300–400-word digest of the file (`level='doc'`). Files under 4,000 characters are their own digest. Digests are derived, so they are not backed up; a changed file (`mobius_docs_full.updated_at` differs) has them rebuilt. Resumable: a rate limit or time limit stops the run and the next carries on from the last finished section.
- **Pace:** by hand (`npm run maintain`) it runs to the end; the daily timed run makes at most 60 model calls and keeps 30% of its time for embedding. Files from linked folders (`<label>/…`) are digested first.
- **At chat time** (`chat.js`): `folderScope()` decides whether the question is about a whole folder or collection ("the documents in Scriptura Fidelium", "across my documents"). A folder name alone does not count, because "Scriptura Fidelium" is also Boon's own term in ordinary talk. If so, the `doc` digests of that folder (or all) go into the context (cap 14,000 chars). A **named long file** (over 20,000 chars) is sent as its `doc` digest plus the section digests that best match the question, together with the usual search passages, instead of being cut at 20,000 characters.
- `findNamedDoc` ignores the `<folder>/` prefix, and a long title is found by its first three words (not for exported chats, whose names end in a hash).
- **Big files:** the live site reads Drive files under 25 MB and keeps 1,000,000 characters per file. Anything bigger (a whole book) goes in from the laptop: `npm run ingest -- "<file or folder>" --label "<linked folder name>"` (no limit, up to 6,000,000 characters; stops at 85% database use), then `npm run maintain` for digests and embeddings. A 1,000-page book is about 3 million characters, ≈ 6,000 search passages, ≈ 45 MB of database.
- **Linked folders cannot be read from the laptop:** the Google token is sealed with `SESSION_SECRET`, which exists only on Vercel. Read them with Settings → "Read new files now" on the live site. (`npm run maintain -- --drive` reads only the old single `DRIVE_FOLDER_ID` folder.)
- Not built: images and scanned PDFs in Drive folders are skipped (a vision model could describe them as they are read).
- **Opening a long Drive file in chat (fixed 4 Oct 2026, after a trace showed a "summary" of a 727,842-character book written from its first 20,000 characters, with no word that most of it was unread):** `workspace.js actOpen` still gives the model the first 20,000 characters, but now (1) says so in capitals, with the percentage, in both the drive result and the context part's title, and the system prompt forbids describing unread parts; (2) **files the whole text in the archive** (`archiveOpened`: under `<linked folder>/<name>` if its folder is linked, so nothing is stored twice, else `Drive/<name>`; refused above 85% database use; capped at 1,000,000 chars) and starts its digest in the background (`chat.js` end of turn, 10 parts at a time; maintenance finishes it); (3) remembers the file as `state.file.archived` in `mobius_state` (12 h). The router flag `aboutOpenFile` (model, plus the `OPEN_FILE_REF` rule when a file was opened) makes follow-ups such as "is his account representative?" use that file even though it is not named; the context then holds the digest (or, while digesting, the parts done so far and how much of the text they cover), plus `passagesFrom()` (full-text search within that one file, which works before any embedding exists).
- `findNamedDoc` compares names without brackets, punctuation and the "(Z-Library)" tag, so "Anglican Theology by Mark Chapman" finds `Anglican Theology (Mark Chapman) (Z-Library).pdf`.
- **Style (system prompt):** conversational prose, never tables, no stacks of headings or bullets unless Boon asks for a list (the drive listings produced by code are exempt). Models that ignore it need a stronger line in `BASE_PROMPT`.

## Keeping the core solid (added 4 Oct 2026) — READ BEFORE CHANGING ANYTHING IN THE CHAT PATH
- **The interface that matters is Mobius ↔ model.** Mobius's identity and memory must survive any model answering. They live in three places and nowhere else: `BASE_PROMPT` (character and rules, `ai/prompt.js`), the memory block built in `chat.js` (marked BACKGROUND ONLY, with the instruction to reply to the new message last), and the model registry (`ai/models.js`: order, `trains`, `weak`, limits). Do not put behaviour in a model-specific branch.
- **`npm test`** (`test/*.test.mjs`, Node's built-in runner, no network or database, under a second) pins the contract: every readable file type, chunking, digest sections, scripture references, folder/theology detection, router rules, the model list (unique keys, privacy flag on every model, small models last, `Ask:` words), the standing lines of the system prompt, and context assembly. **`deploy.bat` runs it and refuses to publish if it fails.** When you change a behaviour on purpose, change its test in the same commit; when you add a feature, add a test for its pure parts.
- **`npm run identity`** asks every configured model the same question through the real transport and system prompt (memory block with one fact, a stale question in the background, "introduce yourself and say what I told you about my sister") and checks: answers as Mobius, claims no vendor identity, uses the memory, prose not a table, answers the new message. Costs one short call per model; run it after adding a model or editing the prompt (`-- --only=key1,key2` for some). 4 Oct 2026: all 13 reachable models passed; a model that failed only because the question was ambiguous showed the check must be worded unambiguously.
- **Readers** (`docs/extract.js`, one entry point `extractFromBuffer`): PDF, Word (.docx), EPUB (spine order, via JSZip), Excel (.xlsx: one block per sheet, tab-separated, cached formula values, dates stay as serial numbers), PowerPoint (.pptx: one block per slide, speaker notes), HTML, and text/Markdown/CSV/JSON/code. Google Docs and Slides export as text, Sheets as CSV (first sheet only). Old binary .doc/.xls/.ppt are refused with a message saying to save them in the new format. To add a type: add it to `extract.js`, to `SUPPORTED_MIME` in `drive.js`, to the `accept` list in `frontend/index.html`, to `KINDS` in `ingest-cli.mjs`, and write a test that builds a tiny file in memory.
- **Translation** needs no code (a model does it) but a long document exceeds one reply: translating a whole file would be a job that works through it section by section, as the digests do. Not built.
- **Groq/Qwen:** the free key allows only 1,000 output tokens a minute for `qwen3.8-27b`, so its `maxTokens` is 900; with 4096 every call was refused as "request too large" and counted as a failure.

## Library mode, private messages, backup (added 4 Oct 2026)
- **Library = shelves.** A linked folder with `mobius_sources.library = true` (Scriptura Fidelium is one) is a shelf. For a theology message (`docs/library.js isTheology`: one strong term such as theology/Anglican/Tillich, or two ordinary ones such as faith + sin; the router's standalone rewrite is tested too) `chat.js` adds two context parts: **the shelf** (one line per book, from its digest, or the bare title while "not yet digested") and **6 passages** from the shelf (`pcm_search_library`, hybrid meaning + keyword; shelf books are cut into passages of about 1,800 characters with no overlap, `LIBRARY_CHUNK` in `docs/store.js`, so each is a paragraph or two and is used as it stands; `rechunk-cli.mjs` re-cuts a shelf; labelled by book; at most 3 per book; an author named in the question, e.g. "Armstrong", gets that book searched on its own). `BASE_PROMPT` "Library:" tells the model to name the book for each point, keep the author apart from its own view, test the argument, and say so when the shelf is silent. The shelf is cached 10 minutes. Books go in with `npm run ingest -- "<folder>" --label "<shelf>"` (from `J:\My Drive\Scriptura Fidelium`), then `npm run maintain` writes digests and embeddings; the live-site folder read is slow and caps a book at 1,000,000 characters.
- **Private messages.** A message starting `Private:` or `Confidential:` is answered only by models with `trains: false` in `models.js` (today Groq's: gpt-oss-120b/20b, Qwen; Groq's stated policy is not to train on API data, verify). It skips web search, the embedding call and automatic learning, runs no memory commands, is **not saved** (saved text would later be read by the digest jobs, which use free models that do train) and its trace entry is blanked. If no private model is available nothing is sent anywhere (`error:no-private-model`). Groq's free daily token allowance is small (gpt-oss-120b: 200,000 tokens a day, nearly used up on 4 Oct), so private messages fall to gpt-oss-20b, a `weak` model.
- **Private shelves.** `mobius_sources.sensitivity = 'private'` keeps that folder's passages, named files and digests out of every prompt that goes to a training model (and switches off the live Drive search while any shelf is private). Set by SQL for now: `update mobius_sources set sensitivity='private' where label='…';`. There is no chat command or Settings control yet.
- **Weak-model badge.** `weak: true` models (ministral-14b, gpt-oss-20b, codestral) make `cascade.js` emit a `weak-model` event after `model:`; the app shows an orange ⚠ on the model badge.
- **Backup.** `npm run backup` (`backend/backup-cli.mjs`) writes one compressed JSON of every `mobius_*` table except the rebuildable (search passages, scripture, traces) and the secret (sealed Google token, passkeys) to `J:\My Drive\Mobius Backup` (the boonlayong Drive, through the Drive desktop app; falls back to `C:\_myProjects\_Mobius\Backup\db`), keeping the newest 7. A hidden watcher (`MobiusBackup.vbs` in the Windows Startup folder, running `backup-cli.mjs --daemon`, log `_dev\backup.log`) starts at login and backs up whenever the newest is over 20 hours old. Delete the .vbs to stop it. **Restore is manual** (read the file, upsert the tables); not yet scripted.

## Settings page (`/settings.html`, gear icon after the refresh icon in the app)
- **Profile:** edit and save (target 3,000 chars; over it, a `deep`-role model condenses it, never refused or chopped; the original stays under earlier versions). **If no model is available the whole profile is kept** (up to 6,000 chars is sent to the model) and housekeeping condenses it later. Mobius also updates it weekly from conversations and **uses the update straight away**, keeping the old version; a manual edit holds the automatic update off for a day.
- **Notes and suggestions:** edit, add, forget; save or drop suggestions (same as the chat commands).
- **Learning mode:** auto / suggest only / off (stored in `mobius_state` key `settings`; `pcm/settings.js`).
- **Models:** read-only status. **Storage & housekeeping:** database use against the 500 MB free plan, last housekeeping report, run it now. **Backup:** everything removed, with Restore.
- API: `GET/POST /api/pcm/profile`, `GET/POST /api/pcm/notes`, `PUT /api/pcm/notes/:id`, `POST /api/pcm/notes/:id/forget|save|drop`, `GET/POST /api/settings`, `POST /api/housekeeping/run`, `GET /api/backup`, `POST /api/backup/:id/restore`, `DELETE /api/backup/:id`.

## Self-cleaning and backups
- **Principle:** nothing Mobius removes is gone. Deleting a document, pruning an old version, retiring a note: each goes to `mobius_trash` (Supabase, the source of truth, restorable for 180 days) and, when Mobius runs on the laptop, is also written as a JSON file to `C:\_myProjects\_Mobius\Backup` (outside the repository: it holds personal documents; `BACKUP_DIR` overrides). Items trashed while running on Vercel are written to the folder the next time Mobius runs locally. If the backup cannot be made, the deletion does not happen.
- **Housekeeping** (`pcm/housekeeping.js`, a step of every maintenance run): mirrors pending trash to the Backup folder; rebuilds documents that have text but no search chunks (reports, never deletes, chunks without text); lapses suggestions unreviewed for 60 days; trashes notes forgotten/rejected over 180 days ago; clears traces over 14 days; clears trash over 180 days (over 360 if never mirrored); measures storage.
- **Drive:** a file removed from the Google Drive folder is removed here too (into the backup), unless more than 30% of files seem to have vanished at once, which is treated as a bad listing.
- **Capacity:** the whole Supabase project is 195 MB of 500 MB (2 Oct 2026); Mobius's document chunks are about 61 MB for 8,100 chunks, so the 15,000-document PCM archive on the laptop drive does NOT fit and stays on the laptop. Google Drive is the next place to attach if Supabase fills.

## Login (passkeys)
- On only when `SESSION_SECRET` is set (set on Vercel, not locally, so localhost stays open). Code: `backend/auth.js`, page: `frontend/login.html`, passkeys in `mobius_passkeys` (RLS on).
- First visit to the live site shows the sign-in page; use `SETUP_CODE` (Vercel env var) to register each device once, then fingerprint / Windows Hello PIN logs in. Sessions last 30 days (signed cookie).
- Passkeys are tied to the site's hostname (`mobius-pwa.vercel.app`); they do not work on localhost, a Tailscale IP or another Vercel domain.

## Mobius's own positions and its understanding of Boon (added 6 Oct 2026) — READ BEFORE TOUCHING THE PERSONA
- **Why:** Boon found Mobius defending Christianity where other AIs stay agnostic. Traces showed no instruction to do so. The causes were: "Disagreement is the default" (so the model argued against whatever he last said, and in a theology chat that landed on the theist side), a theology shelf made only of Christian authors, his own theological summaries in memory, and a different model answering each time, so no position survived to the next message. Rewriting the persona text does not fix that; positions kept in one place do.
- **Positions** (`pcm/stance.js`, `mobius_memory` kind `stance`, one active row per topic, JSON content: position, confidence, because, change, covered[], revised). Seeded balanced on 6 Oct: God, Morality, The Bible, Religion power and violence, Suffering and theodicy. They are Mobius's, not Boon's, and not Claude's: edit them only at Boon's request, and say what changed. `chat.js` selects those whose key or keywords appear in the message (`stancesFor`; short keywords are whole words, so "Godfather" is not God) and sends them as the **first** context part (rank 1, so a small model's trimmed middle never loses them), headed as Mobius's own.
- **Learning** (`maintain.js refreshStances`, step `stances`, plus `learnStancesSoon` after any exchange that touched a position, at most every 20 min): records what was ARGUED (`covered`: point, outcome held/conceded/open) so it is not argued from scratch again. A position changes only when the update carries a new one, and the job's prompt forbids moving it because Boon disagreed, repeated himself, sounded sure, or because an earlier reply (from some other, perhaps careless, model) took a line. A new topic needs its own position. Max 14 topics, 16 covered points each. Older versions stay archived (`pcm_put_memory`).
- **Understanding of Boon** (`maintain.js refreshWorking`, kind `working`, every 2 days from 10+ new messages): what he is working through, how he reasons, what has been covered, how he likes to be answered, in his own provisional words. Lines matching `PRIVATE_TOPIC` are dropped (it rides in prompts that may reach free, training models). No character assessment. Sent as a rank-2 part.
- **Prompt** (`ai/prompt.js`): "Disagree when Boon is wrong and agree when he is right; neither is the default"; "You have positions of your own"; take neither the believer's nor the sceptic's side by default; a practice's faithfulness to a tradition (theology) is not the same question as whether it belongs to the tradition's history; points already argued are not rerun; his faith or doubt is not evidence. Pinned by `test/stance.test.mjs`.

## Answer checks (added 6 Oct 2026)
- **Layer 1, built: plain-code checks** (`pcm/checks.js`, run at the end of `chat.js` on the model's finished answer; skipped for code-made answers such as drive listings and scripture; tests in `test/checks.test.mjs`). `count`: the answer says "three reasons" and numbers a list of another length: a note is added under the answer. `opener`: it begins by agreeing or praising ("You're right", "Great question"). `moved`: it says it has changed its mind while a stance was in force. The last two go to the trace only (`data->'checks'` in `mobius_traces`), to be counted and reviewed. Stance conflicts proper need meaning, so they wait for layer 2.
- **Layer 2, built 6 Oct 2026: a verifying reviewer** (`pcm/review.js`, called from `chat.js` between the cascade and the layer-1 checks; tests in `test/review.test.mjs`, with fakes for the models, the search and the redraft). Decided BEFORE the answer is written (`shouldReview`), because a reviewed answer is **held**, not streamed: Boon sees "thinking" until the checked reply arrives (the server sends `checking` events every 5 s so the connection stays alive; the frontend ignores them). Reviewed: theology (`isTheology`), questions that needed a web search, and questions asking for facts, sources or quotations (`FACT_QUESTION`). Not reviewed: casual talk, questions about Mobius, listings and scripture made by code, attached documents, forced models (`Ask:`), memory commands, private messages, and any question touching `PRIVATE_TOPIC` (the question and draft go to a second provider that may train on them).
  - **The reviewer** is a model of a *different provider* from the one that answered (`askModel(..., { role: 'review', exceptProvider })`; ranks in `models.js`: Gemini first, then nemotron, gpt-oss). It gets the question, the draft and the stored positions that applied, and a fixed checklist. It may raise, from the text alone: `contradiction` (of a stored position, or itself), `missed`, `flattery`, `count`. A claim that outside evidence could settle (`unsupported`: a quotation, source, date, book) is NOT a problem by itself: the reviewer names up to 2 search queries, `tavilySearch(q, { depth: 'basic' })` runs them, and a second reviewer call weighs the results. Only a claim the results **contradict, with a source named**, counts; "could not verify" never does. The code checks of layer 1 (miscount, flattering opener) are added to whatever the reviewer finds.
  - **Redraft once:** if there are problems, the answering cascade is given the turn, its own draft and the problems (with the sources) and writes the reply again; the reply is sent with a line under it, "Checked before sending: revised for …". If the reply cannot be written again in time, the draft is sent with "found …, which I could not correct in time".
  - **Fails safe:** reviewer down, over its allowance, unreadable or too slow, no other provider available, or too little time: the draft goes out exactly as written (`report.skipped` in the trace says why). The whole turn has a time budget, `TURN_BUDGET_MS` in `config.js` (52 s on Vercel, a guess from `CRON_BUDGET_MS`; 110 s locally; env `TURN_BUDGET_MS` overrides): a held draft that outlives the serverless function would be lost, so the review is cut short rather than run past it. **If the Vercel function limit is longer, raise it.** Switch the whole layer off with env `REVIEW_MODE=off`.
  - **Reading it:** `select id, created_at, data->>'query', data->'reviewing', data->'review' from mobius_traces order by id desc limit 10;` shows whether a turn was reviewed, by which model, what it found (`problems`), what was searched, and the verdict (`pass`, `revised`, `flagged`) or why it was skipped. Cost: 1–3 reviewer calls, up to 2 basic Tavily searches (1 credit each) and, when problems are found, one more answer: free quota goes faster, and Gemini's daily allowances are often already spent, so the reviewer is sometimes unavailable.
  - **Not built:** a "checking…" label in the app (the frontend was not to be changed); a Settings switch; a stance-conflict check by meaning outside the reviewer.
- **Layer 3: Claude reviews the traces** from time to time and adjusts prompts and positions; costs Mobius nothing.

## The model bench (`npm run bench`, 7 Oct 2026)
- **Why:** model quality varied far more than expected between runs and between models, and the flagship Gemini models allow only 20 requests a day each, so which models to trust for which job has to be measured, repeatedly, within those limits. `npm run compare` (prayers only) is the forerunner and overlaps with the bench's prayer items; remove it once the bench is trusted.
- **What it measures** (`backend/bench/tasks.mjs`, 12 tasks, 37 items): plain facts, counting and order, no invention for made-up works, holding to the truth under pushback and accepting a good correction, format and house style (two sentences, 40 words, British spelling, no tables), staying Mobius, finding a fact in the notes under the model's own window (built as `chat.js` builds it), summaries that invent no numbers, routing JSON (role `quick`), deciding what to remember (role `learn`), and two items that go through the whole of `chat.js` with Boon's real notes: his prayers and whether the model uses what it has been told about them. Marking is plain code; **every item carries a good and a bad answer and `test/bench.test.mjs` checks that the marking tells them apart.** No model judges a model.
- **How it runs** (`bench/runner.mjs`): unattended, one worker per provider, keeping to each provider's gaps and tokens-a-minute; every answer is appended to `_dev/bench/<batch>/results.jsonl` at once (a shutdown loses at most one call); run again with the same `--batch` to carry on (refused items are retried, finished ones skipped); jobs are ordered pass by pass so stopping at any time leaves balanced data; stops at `--until=HH:MM` or when a file called `STOP` appears in the batch folder. A refusal is classified (`quota`, `daily`, `overload`, `timeout`, `error`); only real errors and timeouts count against reliability. A model whose daily allowance is spent is left alone for the rest of the batch. Per-batch budgets (`BUDGET` in the runner) keep the bench from spending all of a model's allowance: flagship Gemini 8 calls each, other Gemini 90, Groq about 110,000 tokens.
- **Privacy:** the personal items go only to providers Boon already uses (Gemini, Groq); NVIDIA and Mistral get only the made-up items (`--all-providers` overrides).
- **Output:** `report.md` (per role: score, coverage, runs, reliability, refused, overloaded, median seconds, first-token seconds; per task; proposed order against the current one in `models.js`) and `stable-proposal.json`. **It never edits `models.js`.** A proposal is marked provisional below three runs or 80% coverage. `--trend` shows each model's role scores batch by batch; `--daemon` does one quick pass a day in the small hours (not installed: it needs a Startup-folder `.vbs` like the backup watcher, and Boon's say-so).
- **Limits to remember:** one run is not a ranking (the same model scored 0 of 5 and 4 of 5 true quotations on the same request); the bench cannot see depth, warmth or theological care; the facts items are few. Read the full texts of the top models before moving anything in `models.js`.
